# hculap「motion-graphic」skill — Movez の記事の決まりごと化

## 何の文献か

- Claude Code の Agent Skills 形式の repo（MIT）。`references/sources.md` に「Movez の記事（[[web-movez-opus-motion-design-course]]）と、そこが集めた作り手・repo に基づく」と明記し、記事の数字（再生数・指示書の長さ・実行時間）は「記事の報告のままで、この skill が測ったものではない」と断っている
- star 0・fork 1（2026-11-09 に GitHub API で取得）。人気のある skill ではない。**取り上げる理由は、Movez の記事の処方を、エージェントが毎回読む決まりの文に落とした形が全部読めること**。人気のある skill は [[web-opus-howseen-claude-motion-design]]・[[web-opus-whaleyxbt-claude-motion]]
- 設計した手順であり、この手順で作った動画の評価は repo に無い（速さの実測が 1 件あるだけ）

## 書いてあること

### 依頼の長さで段取りを変える（SKILL.md §1、references/prompting.md）

| 段 | 指示書の長さ | 典型の実行時間 | 使いどころ | SKILL.md の段取り |
|---|---|---|---|---|
| L1 一行 | 約 150 字 | 15〜50 分 | エンジンの試験、製品の無いショーリール | 自分で計画して進む。質問しない |
| L2 ブランドの reel | 約 350 字 | 30〜45 分 | URL からのローンチ動画 | 本物の素材を集め、ショットリストを見せて OK を待つ |
| L3 状態の仕様 | 1.5〜3k 字 | 修正込み 1〜2 時間 | UI が変形するループ、実データの製品動画 | 足りない入力を聞き、拍の格子に状態を並べて見せてからコードを書く |
| L4 監督の指示書 | 9.5〜19k 字 | 自律で 6〜12 時間 | MV・物語・数分の作品 | ゲートのある制作として扱い、章に分ける |

（長さと時間は Movez の記事の報告値）。「L1 の一文で L2 以上の仕事を頼まれたら、足りない L2・L3 の構造を自分で書き、製品動画なら動かす前に見せる」とある。L1 の弱点として "brief contagion" を挙げ、「一行はエンジンを試すが、アイデアは試さない。含んでいないから」と Movez の文をそのまま置いている（語の出どころは [[web-opus-athemeroy-awesome-opus-5-5-videos]]）。

### 既定値と描画の決まり（SKILL.md §1・§4、STUDIO.md、engine.md）

- 既定: **15 秒、9:16 の 1080×1920、60fps**、合成した 120BPM の曲、作り手が名前を付けて選んだ「見た目」、画面の文字は依頼者の言語
- 描画方式は既定で **A: コードで描く canvas**。B（Remotion・HyperFrames）は頼まれたときか連作のとき、C（動画・画像モデル）は API キーと予算の承認があるときだけ、D（素材の編集）は素材を渡されたとき
- 描画の約束: `window.seek(t)` は t だけの純関数。描画時に CSS transition・タイマー・requestAnimationFrame・Date・Math.random を使わない（種付き乱数を使う）。フォント・画像はローカルに置き `window.ready` で読み込みを待つ。イージング曲線でなくばね。座標は `layout(W, H)` から出し、16:9・1:1・9:16 を同じ時間軸から作る（切り抜かず組み直す）
- 最終書き出しは 60fps で 1 コマに 4 枚のサブフレームを混ぜてモーションブラー。下書きは 30fps・サブフレーム 1。ラウドネスは −14 LUFS に二段階で正規化
- 速さの実測（README）: 64 秒・1080×1080・60fps・サブフレーム 4（約 15,000 回のブラウザ描画）を、8 vCPU の ARM64 のクラウド機・4 並列で約 4 分

### 決まりごと（house rules）と禁止事項（STUDIO.md、SKILL.md「Hard rules」）

- 作品ごとに `STUDIO.md` を置き、「この作業場で働く全エージェント（サブエージェント含む）がコードに触る前に読む」
- 見た目の禁止: 中央のタイトル＋グラデーション背景、全部フェードイン、四隅のラベル、枠線、UI の縁の発光、汎用のパーティクルの破裂、ありがちな青紫の「テック」グラデーション
- 構成: 最初の 2 秒にフック、**2〜4 秒ごとに新しいことが起きる**、カットは小節頭・状態の変化は拍、連続するショットは違う技法、終わりは解決するか 0 コマ目へループ
- 書体は表示用 1・UI 用 1、アクセント色 1
- 本物の製品の UI・素材・主張だけ。製品の画面を想像で描かない
- 音楽とフォントは権利のあるものだけ（自作・ロイヤリティフリー・合成・ElevenLabs の自分のプラン）

### 批評ループ（SKILL.md §5、references/critique.md）

- 1 拍 1 枚の静止画をコンタクトシートにし（各コマに秒のラベル）、「誇らしげな作者ではなく辛口のモーションディレクターとして」**フック・スマホでの可読性・動き・変化・構図・ブランドの正確さ・音の同期の 7 軸を 1〜10 点**で採点、`docs/review_log.md` に記録、ワースト 3 を直す。**全項目 8 点以上まで。新作は最低 3 回**
- 探すもの: 入れ替わりで文字が重なる、イーズせず滑る、四隅のラベルと枠、中央＋グラデーション、拡大でぼけた文字、何も起きない拍、ループの継ぎ目のつまずき、同じ構図の連続、端に触れる文字、低コントラスト
- 可読性の基準: 360px 幅で全部の語が読め、要の文字は 1 語あたり最低約 0.3 秒画面にある
- 動きは静止画では見えないので、下書きの動画（30fps）と `inspect.sh strip`（連続 12 コマ）で確かめる。安い順に: 静止画（秒単位）→ 下書き動画 → 静止画が収束してから最終レンダリング
- **止める条件**: 2 回続けて最低点が上がらなければ、何が妨げているかを書いて止まって報告する。または約 8 回で止まる
- 納品物に「最後の回の点数、次に直すこと、**正直な回数（"one prompt" と言わない）**」を含める
- 決定性の確認: 同じ秒を別のフォルダに 2 回描いてハッシュを比べる。README は「1・4・6 並列で描いた結果がバイト単位で同一」と書いている

### 長い作品の分担（SKILL.md §4、prompting.md §6）

- 長い作品は先に `docs/ANIMATION_GUIDE.md` を書き、サブエージェントに章（`src/ch/chNN.js`、一つの時間範囲）を一つずつ持たせ、`index.html` で一つの `seek(t)` に縫う。手本は PDoom の MV（[[web-opus-pdoomvideo]]）

## この wiki への含意

- **西尾の方式と骨格は同じ、数値の既定が違う**: 西尾の方式も canvas に時刻の純関数で描き headless Chrome で撮り、120BPM で場面を小節頭に置き、BGM を合成した（[[exp-html-capture-pipeline]]）。違いは、西尾は 16:9 の 1920×1080 から始め（縦長は別ファイル）、サブフレームを混ぜるモーションブラーの記述は経験ページに無く、ラウドネスの目標は英語版で −16 LUFS だった。どれが良いかは比べていない
- **「2〜4 秒ごとに新しいこと」は promo の決まり**: 西尾の promo の経験「変化が止まるとテンションが下がる」「アウトロ 10 秒の静止クレジットは死んだ拍」（[[exp-polis-magi-op]]、[[exp-sutra-hype-editions]]）と一致する。一方で talk の経験は「完全静止を既定に、画面全体の drift は気持ち悪い」（[[exp-qualia-video]]）で、この skill の決まりを talk・embed にそのまま当てると逆になる。この skill は対象を promo・ローンチ・ショーリールと書いていて、解説（"animated explainers"）も対象に挙げているが、解説用に決まりを変える記述は無い
- **批評ループは AI の自己採点で、人の評価の段は L2 以上のゲートだけ**: 西尾の経験は「機械の QA に通っても見やすさは保証されない。人の評価を別の合格条件にする」「動きが大事な版は静止画では評価できない」（[[experience-lessons-2026-11]]）。この skill も「動きは静止画で見えないので下書き動画と連続コマで」と書き、静止画の限界は認めている。違いは合格条件: skill は「全項目 8 点以上」を AI の採点で決め、西尾は人（西尾）の一言で決めた（[[exp-gyazo-resumption-video]] の 12 行のフィードバック表）。Polis では AI の採点がアウトロの「死んだ拍」を見つけた一方、レンダリング前に止めたので採点と人の評価が合うかは確かめていない（[[exp-polis-magi-op]]）
- **止める条件は西尾の経験に無かった**: 「2 回続けて最低点が上がらなければ止まって報告」は、自己採点が空回りする場合への備え。西尾の側では、止まりどころは人の判断（Polis の「メロディが未検証」で公開前に止めた）だった
- 「回数を正直に報告、one prompt と言わない」は、grasp-nishio の「設計意図を検証済みの効果として書かない」（CLAUDE.md の書き方）と同じ向きの決まり
